# Запуск и публикация

## Требования

Node.js 24+, npm, постоянный локальный диск для SQLite. Внешние API, Supabase, OAuth и платные сервисы не нужны. Существующая GitHub-аутентификация среды проверена read-only Git-запросом. Для публикации понадобится сервер/хостинг с Node.js или Docker, постоянным томом и HTTPS-доменом.

## Разработка

```bash
npm ci
npm run dev
```

Приложение слушает порт 3000 на всех интерфейсах. Откройте этот порт в браузере на своей машине или через средства выбранного хостинга. Фронтенд и API работают на одном адресе. База создаётся в `data/workshop.db`, не включается в Git. Другой путь: `DATABASE_PATH=/постоянный/каталог/workshop.db npm run dev`.

Для ограниченного домашнего каталога npm: `npm ci --cache /tmp/workshop-npm-cache`. На Linux для браузерных тестов нужен Chromium: `CHROMIUM_PATH=/путь/к/chromium npm run test:e2e`. При наличии используется `/usr/bin/chromium`; иначе браузер из установки Playwright (`npx playwright install --with-deps chromium`). Путь можно переопределить переменной `CHROMIUM_PATH`. Настройка тестов запускает свой dev-сервер при отсутствии работающего на порту 3000. Браузерные тесты создают учебные комнаты в выбранной БД; не запускайте их против рабочей базы.

```bash
npm test             # методология, экспорт, реальные HTTP/SSE и SQLite
npm run typecheck
npm run build
npm run test:e2e     # разные браузерные контексты, 7 заданий, мобильный экран, конфликт/обрыв сети
npm audit --omit=dev
```

## Как провести воркшоп

1. Ведущий вводит имя и создаёт 2 или 3 команды.
2. На пульте открывает «Пригласить участников». Для каждой команды есть отдельные ссылки капитана, куратора-помощника и участника. Отдельно сохраните секретную ссылку восстановления ведущего.
3. Каждый участник открывает своё приглашение и вводит имя. Ссылки содержат ключ доступа в `#invite=…`, не отправляемый в HTTP URL. После входа ключ убирается из адресной строки и используется HttpOnly-cookie. Одновременно разные роли тестируют в разных профилях/инкогнито: в одном профиле браузера одна текущая сессия.
4. Ведущий запускает 30 минут; может поставить паузу, продолжить, завершить и отправить событие. Время блоков — ориентир, а не запрет перехода. После завершения разрешена доработка ответов.
5. Капитан фиксирует ответы. Участник по умолчанию читает и комментирует; капитан/ведущий может дать ему право записи. Помощник комментирует и даёт подсказки, не подменяя спонсора изменения.
6. Ответы сохраняются на сервере при выборе, выходе из текстового поля или через 700 мс без ввода. Статус показывает сохранение и ошибки. После обрыва сети сохранённые ответы восстанавливаются; неотправленный текст остаётся только в открытой вкладке до успешной повторной записи. При конфликте ничего не перетирается: редактор видит оба варианта и выбирает, какой сохранить.
7. Итоговый план можно открыть в любой момент, доработать, скачать в Markdown/JSON или сохранить в PDF через печать браузера. Ведущий открывает карточку каждой команды и её план.

## Production без Docker

```bash
npm ci
npm run build
NODE_ENV=production \
DATABASE_PATH=/srv/workshop-data/workshop.db \
PUBLIC_ORIGIN=https://workshop.example.org \
COOKIE_SECURE=true \
PORT=3000 npm start
```

Обеспечьте пользователю процесса право записи в каталог БД. Для локальной проверки production по HTTP используйте `COOKIE_SECURE=false` и локальную `PUBLIC_ORIGIN`; для публичной версии оставьте Secure cookies. Переменные передаются окружением; `.env` автоматически приложением не загружается.

Настройте systemd, Docker или процесс-менеджер на перезапуск приложения. Не используйте несколько процессов/реплик: эта версия рассчитана на один сервер и локальную SQLite. 20 участников и 2–3 команды обслуживаются одним процессом. Для нескольких реплик понадобятся PostgreSQL и общая шина событий.

## Docker Compose

```bash
docker compose up -d --build
```

Локальный Compose привязывает порт к интерфейсу loopback хоста; данные хранятся в named volume `workshop-data`. Перед внешней публикацией:

```bash
COOKIE_SECURE=true PUBLIC_ORIGIN=https://workshop.example.org docker compose up -d --build
```

Настройте HTTPS reverse proxy на порт 3000. Docker-образ собран и проверен в этой облачной среде: вход двух ролей, сохранение ответа, общий таймер и восстановление после перезапуска контейнера. Первый build остановился на TLS-сертификате npm-реестра; повторная сборка выполнена с доверенным CA среды через BuildKit secret во временной копии Dockerfile. TLS и контроль целостности пакетов не отключались, сертификат не включён в образ. На целевом хосте повторите сборку с его настройками доверия.

Пример фрагмента Nginx (сертификаты и DNS настраиваются на хосте):

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 1h;
}
```

Для `/api/events` необходимы долгие HTTP-соединения без буферизации, иначе совместная работа задержится. Разрешите исходящий доступ к `registry.npmjs.org` для установки и Docker registry для сборки образа. В рабочем приложении нет внешних шрифтов, аналитики или CDN. После публикации проверьте вход капитана и участника с двух устройств, синхронизацию поля, паузу таймера, обновление страницы и экспорт. Проверка `/api/health` удостоверяет доступность API и БД, но не заменяет этот сценарий.

GitHub Pages и чисто статический хостинг не подходят: нужен работающий backend и постоянная БД. Serverless с временным диском тоже не обеспечивает сохранность этой SQLite-базы.

## Сохранность и доступ

База содержит ответы, имена, комментарии и ключи приглашений. Ограничьте права на каталог, не публикуйте БД или `.env` в Git, настройте шифрование диска и политику хранения данных по правилам организации. Сессия действует 7 дней; восстановление после этого — по секретной ссылке роли. Приглашения действуют, пока существует комната. Ссылки можно использовать повторно: любой получивший ссылку получает соответствующую роль. Ссылки капитана/ведущего не предназначены для общей рассылки. Корпоративный SSO, персональные одноразовые приглашения, отзыв приглашений, удаление комнат и административная панель хранения в эту версию не входят; для открытого размещения ограничьте доступ на reverse proxy/VPN/SSO организации. Авторизация на уровне комнат и ролей уже работает на сервере.

SQLite работает в WAL. Для простого резервирования остановите сервис и сохраните весь том `/data` (или каталог `data` вне Docker); не копируйте один `.db` во время записи, игнорируя WAL. Для резервирования без остановки используйте SQLite Online Backup API/команду `.backup`. Регулярно проверяйте восстановление копии на отдельном диске. Не запускайте `docker compose down -v`, если хотите сохранить результаты.

## Что требуется извне

Для совместной работы с удалёнными участниками: доступный им адрес сервера, HTTPS, постоянный диск, резервные копии и настройки прокси для SSE. DNS, сертификат, учётная запись хостинга и публикация не выполняются автоматически. Добавьте корпоративное ограничение входа при размещении за пределами доверенной аудитории.
