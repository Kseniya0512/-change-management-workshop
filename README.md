# Change Management Game
## Интерактивная игра «Переход на единый корпоративный мессенджер»

### О проекте

Отдельный интерактивный сайт для проведения корпоративного онлайн-воркшопа по управлению изменениями.

**Цель игры:** научить участников применять корпоративный фреймворк внедрения изменений на практическом кейсе перехода компании на единый корпоративный мессенджер.

Участники должны не просто отвечать на вопросы, а за 30 минут разработать первоначальный план внедрения изменения.

### Формат воркшопа

- 20 участников.
- 2–3 команды.
- В каждой команде куратор-помощник.
- Один общий ведущий.
- Продолжительность игры — 30 минут.
- Команды обсуждают решения и совместно формируют план.
- Игра проходит онлайн через браузер.
- Результаты каждой команды сохраняются.

### Игровой кейс

**Название:** «Один мессенджер — одна компания».

**БЫЛО:**

- Сотрудники используют разные мессенджеры.
- Важные рабочие сообщения теряются.
- Информация дублируется.
- Нет единого канала корпоративных коммуникаций.
- Руководителям сложно организовать единое информирование.
- Новым сотрудникам сложно разобраться в рабочих чатах.

**СТАЛО:**

- Все сотрудники переходят на единый корпоративный мессенджер.
- Есть единое пространство рабочих коммуникаций.
- Сокращаются потери важных сообщений.
- Упрощается взаимодействие между подразделениями.
- Устанавливаются единые правила коммуникаций.

**Важное условие:**

Новый корпоративный мессенджер периодически зависает, сообщения могут приходить с задержкой, а IT-команда ещё устраняет технические проблемы.

Часть сотрудников сопротивляется переходу, поскольку привычные мессенджеры работают стабильнее.

### Цель изменения

Обеспечить устойчивый переход сотрудников на единый корпоративный мессенджер, повысить эффективность внутренних коммуникаций и снизить количество пропущенных важных сообщений.

### Методология

Игра основывается на корпоративном фреймворке управления изменениями.

**Пять шагов процесса:**

1. Уведомление ЦЭИ.
2. Совместная оценка применимости фреймворка.
3. Подготовка плана внедрения.
4. Реализация изменения.
5. Сбор обратной связи и корректировка.

**Четыре этапа внедрения:**

1. Подготовка.
2. Старт.
3. Основная часть.
4. Завершение.

Для оценки применимости используются восемь критериев корпоративного фреймворка.

### Экраны игры

**Экран 1. Было / Стало и цель**

Участники определяют, что меняется и какого результата необходимо достичь.

**Экран 2. С чего начать?**

Выбирают правильную последовательность действий и момент подключения ЦЭИ.

**Экран 3. Это изменение или информирование?**

Оценивают ситуацию по восьми критериям применимости фреймворка.

**Экран 4. Участники и роли**

Определяют затронутые группы, инициатора, спонсора, руководителя проекта, команду изменений и чемпионов.

**Экран 5. Подготовка плана**

Выбирают маршрут внедрения и распределяют действия по четырём этапам. Определяют сроки, ответственных и контрольные точки.

**Экран 6. Метрики успеха**

Выбирают показатели, устанавливают цели и определяют способы измерения.

**Экран 7. Коммуникации**

Формируют последовательность вовлечения руководителей, чемпионов и сотрудников.

**Экран 8. Сопротивление и план Б**

Решают игровую ситуацию с техническими сбоями, сопротивлением сотрудников и необходимостью корректировки плана.

**Экран 9. Завершение**

Оценивают результаты внедрения и определяют дальнейшие действия.

### Игровая механика

Используются:

- Интерактивные карточки.
- Вопросы с вариантами ответов.
- Зелёная и красная подсветка ответов.
- Сопоставление ролей и действий.
- Перетаскивание карточек по этапам.
- Выпадающие списки.
- Подсказки ЦЭИ.
- Неожиданные игровые события.
- Возможность исправлять решения.
- Индикатор прогресса и таймер.

Правильные и неправильные ответы используются для проверки правил фреймворка. Управленческие решения оцениваются с учётом аргументации.

### Результат игры

По мере прохождения заданий автоматически формируется **план внедрения корпоративного мессенджера**, содержащий:

- Было / Стало.
- Цель изменения.
- Оценку применимости фреймворка.
- Выбранный маршрут внедрения.
- Роли и заинтересованные стороны.
- План действий по четырём этапам.
- План коммуникаций.
- Метрики успеха.
- Риски и работу с сопротивлением.
- Каналы поддержки и обратной связи.
- План Б.
- Завершение и закрепление изменения.

План формируется из реальных ответов команды и доступен для просмотра и экспорта.

### Технические требования

- Отдельный веб-сайт на русском языке.
- Современный корпоративный дизайн.
- Адаптация под компьютеры участников.
- Синхронизация команд в реальном времени.
- Отдельные роли ведущего, капитана, куратора-помощника и участника.
- Сохранение прогресса.
- Таймер 30 минут.
- Экспорт итогового плана команды.

### Основной принцип

**Цель игры — научить участников самостоятельно готовить план внедрения изменения, а не просто угадывать правильные ответы.**

Игра должна помогать участникам понимать, зачем нужны ЦЭИ, оценка готовности, планирование, коммуникации, работа с сопротивлением и метрики успеха.

## Реализованное приложение

Полноценный сайт на React + TypeScript и Node.js 24 / Express с SQLite на сервере и SSE-синхронизацией. Реализовано **последнее дополнение docs/game-spec.md**: вводная, семь заданий и финал, 30 минут, 8 критериев с порогом 2, 2 метрики принятия. В репозитории только один игровой кейс — корпоративный мессенджер. Корпоративные исходные материалы сохранены.

```bash
npm ci
npm run dev
```

Сервер работает на порту **3000**. Для совместной игры участникам нужен общий доступный адрес этого сервера. Ведущий создаёт воркшоп и раздаёт отдельные приглашения каждой роли. Ответы хранятся в `data/workshop.db`; localStorage не используется для ответов или синхронизации.

Проверки: `npm test`, `npm run typecheck`, `npm run build`, `npm run test:e2e` (Chromium). Production: после сборки `NODE_ENV=production npm start` за HTTPS-прокси с постоянным диском. Для локального HTTP-тестирования production добавьте `COOKIE_SECURE=false`.

Подробно: [запуск, проведение воркшопа, Docker, публикация, резервирование и ограничения](docs/deployment.md). Для публикации подготовлены `Dockerfile` и `compose.yaml`. GitHub Pages не поддерживает необходимый backend.

Презентация «Внедрение изменений в проектах и процессах HR» отсутствует и не использовалась. Источники и разрешённые расхождения перечислены в инструкции.
